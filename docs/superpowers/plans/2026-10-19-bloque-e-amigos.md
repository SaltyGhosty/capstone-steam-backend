# Bloque E — Amigos y perfil: plan de implementación

> **Para agentes:** lee primero `docs/superpowers/plans/2026-10-19-oleada-1-comun.md` (reglas obligatorias). Pasos con casillas `- [ ]`.

**Objetivo:** los jugadores se buscan, se mandan solicitudes de amistad y ven el perfil de otros (biblioteca con horas jugadas y amigos). El perfil es privado por defecto: solo lo ven los amigos, salvo que el dueño lo haga público.

**Spec:** `docs/superpowers/specs/2026-10-19-cierre-y-extras-design.md` §4 «Bloque E». **Migración: V9.**

## Decisiones ya tomadas

- **Solo cuentas de jugador** participan: las que no tienen `ROLE_DEVELOPER` ni `ROLE_ADMIN` y están `enabled`. Cualquier otro usuario es invisible:
  - búsqueda: no sale;
  - perfil: 404 `notFound.user`;
  - solicitud: 404.

  Si el que pide es developer o admin → 403 `friend.playersOnly`.
- **Una fila por pareja**, sea cual sea la dirección. Columnas `user_low_id` y `user_high_id` (el menor y el mayor de los dos ids), con `UNIQUE(user_low_id, user_high_id)`: SQL portable, sin índices por expresión.
- **Solicitud cruzada:** si A pide a B y B ya tenía una pendiente hacia A, se acepta esa y la respuesta es `ACCEPTED`.
- **Visibilidad del perfil** (en el backend): se ven biblioteca y amigos si quien mira es el propio usuario, es amigo (ACCEPTED) o `profilePublic = true`. Nunca salen email, pedidos, carrito ni wishlist.
- Todas las rutas requieren sesión (la regla `anyRequest().authenticated()` ya lo cubre).
- `username` «me» no puede existir (mínimo 3 caracteres), así que `/api/users/{username}/...` no choca con `/api/users/me`.

## Interfaces que fija este plan

- **SQL de V9:**
  - `ALTER TABLE users ADD COLUMN profile_public BOOLEAN DEFAULT FALSE NOT NULL;`
  - tabla `friendships`:
    - `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
    - `requester_id BIGINT NOT NULL`, `addressee_id BIGINT NOT NULL`
    - `user_low_id BIGINT NOT NULL`, `user_high_id BIGINT NOT NULL`
    - `status VARCHAR(10) NOT NULL`
    - `created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL`
    - `responded_at TIMESTAMP WITH TIME ZONE`
    - restricciones:
      - `uk_friendships_pair UNIQUE (user_low_id, user_high_id)`
      - FKs a `users(id)` `ON DELETE CASCADE`
      - `ck_friendships_status CHECK (status IN ('PENDING','ACCEPTED'))`
      - `ck_friendships_not_self CHECK (requester_id <> addressee_id)`
      - `ck_friendships_order CHECK (user_low_id < user_high_id)`
  - índices: `idx_friendships_addressee (addressee_id, status)` y `idx_friendships_requester (requester_id, status)`.
- **DTOs** (`friend/dto`):
  - `UserCard(String username, String displayName, String avatarUrl)`
  - `SearchHit(UserCard user, Relation relation, Long requestId)`
  - `enum Relation { SELF, FRIENDS, REQUEST_SENT, REQUEST_RECEIVED, NONE }`
  - `FriendResponse(UserCard user, Instant since)`
  - `FriendRequestResponse(Long id, UserCard user, FriendshipStatus status, Instant createdAt)`, donde `user` es la **otra** persona
  - `FriendRequestsResponse(List<FriendRequestResponse> incoming, List<FriendRequestResponse> outgoing)`
  - `SendFriendRequest(@NotBlank String username)`
  - `ProfileGame(Long gameId, String title, String slug, String coverUrl, int playtimeMinutes)`
  - `PublicProfileResponse(UserCard user, Instant memberSince, boolean profilePublic, Relation relation, Long requestId, boolean visible, List<ProfileGame> library, List<FriendResponse> friends)`: `library` y `friends` son `null` si `visible == false`.
- **Endpoints:**

  | Verbo | Ruta | Respuesta |
  |---|---|---|
  | GET | `/api/users/search?q=` | `List<SearchHit>`, máx. 20. `q` de al menos 2 caracteres sin espacios, si no 400 `friend.queryTooShort`. Busca sin distinguir mayúsculas en username o displayName. Se excluye a sí mismo. |
  | GET | `/api/users/{username}/profile` | `PublicProfileResponse` |
  | GET | `/api/friends` | `List<FriendResponse>`, ordenados por displayName |
  | GET | `/api/friends/requests` | `FriendRequestsResponse` |
  | POST | `/api/friends/requests` | body `SendFriendRequest` → 201 `FriendRequestResponse` (status PENDING, o ACCEPTED si era cruzada) |
  | POST | `/api/friends/requests/{id}/accept` | 200 `FriendRequestResponse`. Solo el destinatario de una PENDING; si no, 404 `notFound.friendRequest`. |
  | POST | `/api/friends/requests/{id}/reject` | 204 (borra la fila). Solo el destinatario. |
  | DELETE | `/api/friends/requests/{id}` | 204. El solicitante cancela su PENDING. |
  | DELETE | `/api/friends/{username}` | 204. Borra la amistad ACCEPTED; si no existe, 404 `friend.notFriends`. |

- **Errores de la solicitud:**
  - a sí mismo → 400 `friend.self`
  - ya son amigos → 409 `friend.alreadyFriends`
  - ya la pediste → 409 `friend.alreadyRequested`
- **`UserResponse`** añade `boolean profilePublic` al final. **`UpdateProfileRequest`** añade `Boolean profilePublic` al final (null = no cambia).
- **Biblioteca del perfil:** `LibraryRepository.findByUserId(userId, PageRequest.of(0, 100, Sort.by(DESC, "acquiredAt")))` mapeado a `ProfileGame`.

## Foco de revisión

1. La visibilidad se decide en el backend: un no amigo nunca recibe `library` ni `friends` de un perfil privado.
2. Dos solicitudes simultáneas cruzadas: la UNIQUE del par evita duplicados. El segundo insert que choque → 409 (`DataIntegrityViolationException` ya da 409).
3. Una cuenta desactivada desaparece de búsquedas y perfiles.
4. La búsqueda escapa `%` y `_` del `q`, o usa `lower(...) like lower(concat('%', :q, '%'))` con parámetro: nunca concatena SQL.
5. Ningún DTO de este bloque expone `email`.
